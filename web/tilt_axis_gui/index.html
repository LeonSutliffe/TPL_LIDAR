Step-and-stare range & capture
—
Start Scan pushes these onto scan_aggregator's parameters, then calls ~/start_scan — which homes the tilt axis first, so make sure the area is clear. Move → settle → capture at each stop, no motion blur. The estimate above is a floor, not a real prediction — it's stop count × (settle + capture time), where capture time uses the RPM field on the VLP-16 tab (higher RPM = faster spin = less capture time needed per revolution, and vice versa) — it's whatever's typed there, though, not confirmed against what the sensor is actually spinning at. It excludes homing and every move between stops entirely, since per-stop move time (accel ramp + actual travel) hasn't been empirically measured yet — see Open Items in HANDOFF.md. Real total will be longer.
Continuous sweep scan
Start Sweep Scan homes, then sweeps continuously between Min/Max, merging the cloud live as it moves — faster coverage than step-and-stare, but points are captured while moving, so expect some motion blur/smear (worse at higher speeds). With Duration=0 it keeps accumulating points in RAM until you press Stop Scan — fine for a bounded session, but don't leave it running unbounded for a very long time. Edge margin discards clouds captured within that many degrees of either turnaround, where the axis is changing direction — the live status line shows how many clouds have been dropped this way.

Mount calibration
Runs a sweep across the Min/Max range set above in Continuous sweep scan, automatically finds a flat surface in it (no ROI, no markers -- just point it at a real wall first, ideally a larger room for more tilt-range leverage), and solves for mount_roll_deg/mount_pitch_deg. Doesn't touch mount_yaw_deg at all -- a yaw error can't be recovered this way (see README), and it's also not the cause of the double-image/skewed-image symptoms this fixes; roll/pitch are. "Calibrate Mount" only computes a result for review; "Calibrate & Apply" applies it immediately once the sweep finishes, no extra click.

Every scan saves here first, on the Pi's own SD card -- much faster than the USB stick -- and each one is downloadable straight from this page. VLP-16 — sensor hardware configuration (set once, not per scan)

Motor / return type / field of view
Physical spin rate. Below 300 rounds up to 300; 0 or below powers the motor down and disables the lasers entirely. Also pushes this value automatically into velodyne_driver_node's own rpm parameter (descriptive only, doesn't itself command the sensor) AND scan_aggregator's rotation_rate_hz (rpm/60, which drives real per-stop capture duration during a scan — see the Scan tab's time estimate) — both stay in sync without a separate step.
Which echo(es) of each laser pulse get kept. Strongest/Last each report one point per pulse; Dual reports both where a pulse produces two distinguishable returns (e.g. a leafy edge, a partially-reflective surface) — more points there, at the cost of roughly double the data rate.
Sensor stops firing lasers below this azimuth (0-359°) — a hardware exclusion, not a post-capture filter. Lasers simply never fire into that arc at all.
Sensor stops firing lasers above this azimuth (0-359°) — same hardware-level exclusion as FOV start, together they define the excluded arc.
This FOV is a hardware-level exclusion zone (useful for e.g. never firing lasers toward an operator's usual standing spot) — different from the Scan tab's View direction/width, which crops already-captured points in software and is meant to vary per scan.
Sensor mount offset (tilt axis → VLP-16)
Translation from the tilt axis's own centre of rotation to the VLP-16's origin, in the tilt axis's own (rotating) frame — X/Y/Z per REP-103 (X forward, Y left, Z up). This is the physical lever arm: how far off-axis the sensor actually sits, measured or estimated by hand. Getting this right matters most for near-range points and multi-station registration; it barely affects far-range geometry.
Rotation of the VLP-16's own frame relative to the tilt axis, applied roll then pitch then yaw — corrects for the sensor not sitting perfectly square on its mount (a slight tilt/twist in how it's bolted down). Small values (well under a degree of real-world misalignment) can still visibly bend a merged cloud at long range, so this is usually the more sensitive half of the two rows here.
Negates the given axis of every merged point in scan_aggregator's output, on top of the rotation above. Not the same kind of correction as Roll/Pitch/Yaw — those only ever compose a proper rotation (determinant +1), which can never flip just one or two axes while leaving the rest alone (that's a reflection, determinant -1). If a scan comes out mirrored/upside-down no matter what Roll/Pitch/Yaw you try, that's the tell you need one of these instead — confirmed necessary for this rig's mount (2026-08-22): Z alone fixed upside-down but left X/Y mirrored, needing two of these three on together to fully correct it. Lives on scan_aggregator, not vlp16_config, so it's a separate live-apply from the Roll/Pitch/Yaw fields above, but this same Apply button pushes both.
Top-down schematic (viewed from above, +X = forward is up) — the shaft and the small dot at its centre never move; that dot is the tilt axis's own centre of rotation. The PUCK is everything that moves, connected to that fixed point by a dashed lever-arm line — the dashed rings are a static distance reference (50mm/100mm at this scale) to make small movements easier to judge, not a real boundary. The three short lines are the puck's own rotated X/Y/Z axes. Z offset (height) isn't shown positionally — currently 0.000 m. Large offsets are clamped so the puck stays on-diagram.
Applies live — vlp16_config re-broadcasts the tilt_link → velodyne transform immediately (Offset X/Y/Z, Roll/Pitch/Yaw), and scan_aggregator picks up the Invert X/Y/Z checkboxes for its next merge (Invert Z/X/Y above), no restart needed for either — and both are remembered for next time (persisted the same way every other setting on this page is). The offset/rotation fields used to be a fixed value baked into the URDF requiring an edit + rebuild to change; now it's just these fields. Use this to fine-tune a merged scan's geometry (e.g. against a known planar target) without touching code.
Network configuration
The sensor's own address on the network. Changing it moves where every command on this tab needs to point — update "Device IP" below (and velodyne_driver_node's launch-time device_ip) to match, or you'll lose contact with it.
Subnet mask for the sensor's interface — must match what your PC's NIC is configured for to reach it directly (factory default 255.255.255.0, a /24).
Default gateway for the sensor's interface. Only matters if you're reaching it through a router rather than a direct or switched connection.
On makes the sensor request an address automatically instead of using the fixed IP/netmask/gateway above — only enable this if a DHCP server actually exists on that network, otherwise the sensor can become unreachable until factory-reset.
Riskiest button on this tab — double check every field above before applying. If the sensor becomes unreachable afterward, you'll need to reach it at the new address directly (or factory-reset it) to recover.
Host ports
UDP port the sensor sends point-data packets to. Must match velodyne_driver_node's own "port" parameter (default 2368, set at launch) or the driver won't receive anything.
UDP port the sensor sends its position/status packets to (default 8308) — separate from the data port above, not currently consumed by anything in this project.
Configuration actions
Persists whatever's currently active on the sensor across power cycles. Every setting above takes effect immediately on Apply/Set, but reverts to what was last saved here if the sensor loses power before you press this.
Reboots the sensor in place — expect roughly a power-cycle's worth of downtime (no point cloud data) while it restarts. Doesn't change any setting, just restarts with whatever's currently saved.
Sensor wiring (this node's own settings)
Where vlp16_config's own HTTP client sends every command on this tab — must match the sensor's actual current address (see Network configuration above). Changing this field alone does NOT change the sensor's address, only where commands get sent; independent of velodyne_driver_node's own device_ip (launch-time only, not live-editable here).

Home Wi-Fi
Changes the stored network profile this Pi joins for internet/SSH at a fixed location. If it's the currently-active connection (see above), saving new credentials can drop this session and any other device connected through it the next time the Pi reconnects — that's this rig's own real WiFi setup being changed, not a scan setting. Takes effect on the next automatic (re)connect, not applied immediately.
Hotspot (this Pi's own fallback network)
